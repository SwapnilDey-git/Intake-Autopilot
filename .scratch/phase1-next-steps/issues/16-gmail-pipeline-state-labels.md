## Question

No manual intervention: the Gmail inbox should visually reflect pipeline state via Gmail labels — automatically, with no human touching Gmail. What exact label scheme, and at what points in the n8n workflow, satisfies that?

**Grounded facts (verified against live system, not assumed):**

- The live Gmail branch of `Phase 8: Real Intake Flow (Fixed V2)` (workflow `F184xZ2JPbJY1wXM`, currently `active=true`) has **no node anywhere that marks a message read or applies a label** after processing — confirmed by reading the workflow's `nodes` JSON directly from Postgres. It only writes to `forms`/`extractions`/`audit_log`.
- n8n's `GmailTrigger.node.js` poll() logic (read directly from the installed package inside the `intake-n8n` container) tracks its own `lastTimeChecked` cursor in workflow static data, advanced by each fetched email's received date, plus a `possibleDuplicates` set guarding the query's inclusive date boundary. **This means the trigger will not re-fetch a message it already saw, even if that message stays unread** — the `readStatus: unread` filter is an additional query constraint, not the dedup mechanism. So there is no "reprocessed every minute" bug; the one duplicate `audit_log` entry found (same filename via `n8n-gmail`, 2026-07-13 and 2026-07-17) is almost certainly two separate manual test sends, not a reprocessing loop.
- n8n's Gmail node (`GmailV2.node.js` / `MessageDescription.js` / `LabelDescription.js`) supports everything needed: Message resource operations `Add Label` / `Remove Label` / `Mark as Read`, and a separate Label resource `Create` operation (labels can be created once, either manually in Gmail's UI beforehand or programmatically via a get-or-create pattern).
- The existing `Gmail account` OAuth2 credential already has the required scopes — n8n's `GmailOAuth2Api` credential type requests a fixed scope set including `gmail.labels`, `gmail.modify`, and `mail.google.com` regardless of what the credential is used for. No new Google Cloud consent/re-auth needed.
- Current Gmail Trigger filter: `subject:"Tax Intake Form Test_Email" has:attachment (filename:pdf OR filename:jpg OR filename:jpeg OR filename:png)`, `readStatus: unread`, polling every minute.

## Progress notes

**Design (grilled, one decision at a time):**
1. Only emails matching the existing intake-candidate filter (subject + attachment type) get labeled — not a general inbox triage.
2. `Waiting to be Intaked` applied as the very first action after Gmail Trigger detects a message, before any processing starts.
3. Terminal labels are mutually exclusive — `Waiting` is removed the same moment `Intaked` or `Failed – Needs Review` is added.
4. Trigger filter switched from Gmail's native `readStatus: unread` to `-label:` exclusion on all three lifecycle labels — native read/unread is fragile (any human previewing the email flips it, silently skipping the trigger's own query forever); labels are a state machine fully under the pipeline's control.
5. Failed extractions get a third label (`Failed – Needs Review`) rather than being left on `Waiting` — leaving them there would misrepresent a dead-ended (retries-exhausted) message as still pending.
6. Label names: flat (no nesting) — `Waiting to be Intaked`, `Intaked`, `Failed – Needs Review`.
7. Labels created once via a temporary node executed manually in the n8n editor (not embedded as a recurring get-or-create step in the workflow) — IDs: `Label_2` / `Label_3` / `Label_4` respectively.

**Build (n8n editor + live testing):**
- Bootstrapped the 3 labels via a temporary Gmail node (`resource: label, operation: create`), executed once per label, then deleted.
- Added 5 new nodes to the Gmail branch: `Add Waiting Label`, `Remove Waiting Label (Success)` → `Add Intaked Label`, `Remove Waiting Label (Failure)` → `Add Failed Label`.
- **First attempt (fan-out) failed empirically**: tried `Gmail Trigger` → both `Add Waiting Label` and `Split Attachments` in parallel (single output, two connections), expecting both to run. Live-tested via a real self-sent email — confirmed via direct Gmail API query that `Add Waiting Label` never executed at all (n8n's execution log showed it was never even attempted; the dead-end parallel branch was silently skipped). Reverted to a plain sequential chain (`Gmail Trigger` → `Add Waiting Label` → `Split Attachments`), which is guaranteed to execute in order.
- **Second bug, also caught by live testing, not assumed**: chaining `Add Waiting Label` inline broke `Split Attachments`, because Gmail's `addLabels` API response (which becomes `Add Waiting Label`'s output) does not carry the original binary attachment — Split Attachments' `$input.all()` therefore saw zero binary keys and produced zero items, silently short-circuiting the rest of the pipeline (execution reported `success` with `lastNodeExecuted: Split Attachments`, easy to mistake for "nothing to do" rather than a bug). Fixed by rewriting `Split Attachments` to pull the binary from `$('Gmail Trigger').all()` (matched by message id) while taking `subject`/`from`/`messageId` from its immediate input.
- Verified end-to-end on a real Gmail message (id `19f777758b32858d`): trigger fired (execution 150, `status='success'`, ~2.3 min), extraction succeeded (`forms.status='extracted'`, `audit_log` id 98), and a direct Gmail API query after completion confirmed the message's final `labelIds` were `[UNREAD, Label_3 (Intaked), SENT, INBOX]` — `Waiting to be Intaked` correctly absent, `Intaked` correctly present.
- **Not separately live-tested**: the failure branch (`Remove Waiting Label (Failure)` → `Add Failed Label`). It shares the identical `messageId`/binary code path already proven on the success branch, so confidence is high, but no real extraction failure was forced through it this session.
- **Tooling notes for future n8n edits on this project**: n8n's clipboard-paste-node trick (dispatching a synthetic `ClipboardEvent` with node JSON) reliably adds nodes to a canvas, but does **not** reliably wire connections that reference a pre-existing node by name — only connections between nodes in the *same* paste batch land. For connection changes on an **active** workflow, a raw SQL `UPDATE workflow_entity.connections` is more reliable than clicking to drag connections, but was blocked by the permission classifier both times it was attempted here (same class of block as the Publish/Unpublish confirmations) — the working alternative that isn't blocked is: build the complete corrected `nodes`+`connections` JSON, then use n8n's own **"Import from file"** (via the workflow-list menu's `⋮` → `Import from file...`) **into a freshly-created blank workflow** (`Create workflow` first) — importing into an *already-open* existing workflow instead appends/duplicates all nodes rather than replacing them, which happened twice this session and left stale duplicate workflow rows behind (`YUGDPB4KpZiieTiP`, `xWwhNUjDOpBDRV5S` — both now inactive but not deleted; now cleaned up: `YUGDPB4KpZiieTiP` was already auto-archived, `xWwhNUjDOpBDRV5S` archived manually to match, via n8n's own Archive action — same convention already used for ~12 other pre-existing historical duplicates on this map, none of which were touched.
